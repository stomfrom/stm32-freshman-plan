# P09 提示：FreeRTOS 入门：多任务数据采集器

## 知识点

1. 实时操作系统（RTOS）解决的核心问题：让多个功能各自独立跑，不用把裸机主循环写成一大串状态机。
2. 任务与调度：每个任务像一个独立的小程序，调度器按优先级和节拍轮流让它运行。
3. 任务状态：就绪、运行、阻塞、挂起；调用 `vTaskDelay` 会让任务进入阻塞态并让出 CPU。
4. `vTaskDelay` 与 `HAL_Delay` 的区别：前者主动让出 CPU 让别的任务跑，后者是原地空等、浪费 CPU 时间。
5. 队列：任务之间传递数据的通道，先进先出，天然解决"多个生产者一个消费者"的同步问题，比全局变量安全。
6. 信号量：用于任务之间的同步（如"中断通知任务数据处理完了"）；互斥锁用于保护共享资源不被同时访问。
7. 优先级与抢占：高优先级任务就绪时会抢占低优先级任务；优先级设置不当会造成低优先级任务长期得不到 CPU（饿死）。
8. 栈的作用与水位：每个任务有自己独立的栈，栈不够会溢出并破坏内存，用栈水位接口查看实际用了多少。
9. `configTOTAL_HEAP_SIZE`：FreeRTOS 自己的堆大小，任务、队列、信号量都从这里分配，设太小会在创建时失败。

## 常见坑

- **任务创建失败但编译通过**：堆空间（`configTOTAL_HEAP_SIZE`）不够，任务创建函数的返回值没检查；一定要检查返回值。
- **CMSIS-V2 的栈单位是字节**：`osThreadAttr_t.stack_size` 填的是**字节数**，而 CubeMX 界面里的 Stack Size 填的是 **words（字）**，两者差 4 倍（界面填 256 = 运行时 1024 字节，代码里填 256 就只有 256 字节）；跑 `printf` 的任务至少给 1024 字节。
- **任务栈溢出导致各种奇怪现象**：栈给小了会随机破坏别的内存，表现为"没改代码但行为变了"；用栈水位检查，别靠猜。
- **`HAL_Delay` 不是 `osDelay`**：`HAL_Delay` 是忙等——不让出 CPU、不进入阻塞态，但它**不会关闭调度器**（高优先级任务仍能抢占，同优先级靠时间片轮转导致时序抖动，低优先级任务会被饿死）；真实危害是占满 CPU、浪费电、时序抖动。RTOS 里统一用 `osDelay(ms)`（CMSIS-V2）或 `vTaskDelay(pdMS_TO_TICKS(ms))`（原生，需 include `FreeRTOS.h` 与 `task.h`）。
- **优先级反转**：低优先级任务占着共享资源、高优先级任务等它，中优先级任务插进来导致高优先级被拖住；用互斥锁的优先级继承机制解决。
- **中断里调用非 FromISR 版本 API**：在中断服务函数里必须用带 `FromISR` 后缀的版本（如 `osMessageQueuePutFromISR` / `xQueueSendFromISR`），并配合 `portYIELD_FROM_ISR()`；用错会崩。另外，会调 FreeRTOS API 的 ISR，其抢占优先级数值必须 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`（默认 5），配成 0~4 会触发断言或静默 HardFault。
- **共享串口不加保护**：两个任务同时 `printf` 会输出交叉的乱码，必须加互斥锁或统一由一个上报任务负责。

## 调试技巧（无逻辑分析仪时的替代手段）

- **每个任务打一条带时间戳的日志**：从日志能看出哪个任务没在跑、哪个任务跑得太频繁，一张日志就能看出大部分调度问题。
- **用 GPIO 翻转标记任务切换**：在任务入口/出口翻转不同引脚，示波器能看出各任务的时间占用比例。
- **栈水位直接打印**：把 `uxTaskGetStackHighWaterMark` 的返回值打印出来，用数字判断栈够不够，比试错法安全。
- **先减到最简再逐个加回**：出问题时先只留一个任务确认系统正常，再一个一个加回任务，能快速定位是哪个任务引入的。
- **看堆剩余量**：周期性打印 `xPortGetFreeHeapSize` 的返回值，能发现内存泄漏或堆不足的早期征兆。
