# P10 提示：独立选题结课项目：完整作品

## 知识点

1. 选题的合适尺度：一个自己熟悉的小功能 + 一两样新东西；纯新东西风险高，纯重复练不到手。
2. 需求说明的写法：不做功能列表的堆砌，而要写清"用户是谁、什么场景、最少要做到什么"。
3. 器件清单的作用：把"要买什么、买几个、买来干什么"写清楚，避免做到一半发现少个东西等快递。
4. 接线图与原理图的区别：接线图只关心"哪个引脚接到哪里"，适合面包板搭建；原理图还要体现电气关系，为后面画板做准备。
5. 系统框图：把功能拆成模块、标出数据流向，是写代码前最有价值的一步，能提前发现接口对不上的问题。
6. 模块化的判断标准：这个模块能不能不改代码就换个引脚/换块屏/换个传感器？能，就说明封装到位了。
7. 演示型项目的三个验收维度：能不能用（功能齐全）、稳不稳（连续跑不崩）、讲不讲得清（能解释每个设计决定）。
8. 复盘的价值：把"最大难点"和"重做会改什么"写清楚，比项目本身的完成度更能体现能力增长。

## 常见坑

- **选题太大做不完**：想一口气做"智能家居系统"，结果 4 周连传感器都没读通；宁可做小做完整。
- **器件没提前确认，做到一半卡住**：某个传感器型号买错、某块模块需要 5V 而手头只有 3.3V，提前列清单并找指导人过一遍能避免。
- **所有代码堆在 `main.c`**：最后想改一个功能要在几百行里找，模块化不是"好看"，是能让你改得动。
- **成品只能接电脑跑**：调试器拔了就不工作，多半是程序没烧进 Flash 或依赖在线调试，交付前一定单独上电测一遍。
- **没有异常场景测试**：交上去才发现连按按键会死机，测试至少要覆盖断电重上电、快速操作、异常输入三类。
- **演示时讲不出为什么**：代码是抄来的、模块是别人写的，一问就露馅；宁可功能少一点也要每行代码都讲得清。

## 调试技巧（无逻辑分析仪时的替代手段）

- **从能跑的最小系统开始**：先让 LED 闪 + 串口能打印，再一个功能一个功能往上加，每加一个就测一遍。
- **保留可回退的版本**：每完成一个功能就 Git 提交一次，改坏了能立刻回退，比在代码里注释掉一大片更可靠。
- **日志分级**：把串口日志分成"启动信息""关键事件""调试细节"三类，演示时只开前两类，输出干净看得清。
- **让同学当用户测一遍**：自己测总有盲区，请没参与的同学照着使用说明操作一遍，能发现大量"只有我知道怎么用"的隐含前提。
- **现象记录优先于猜测**：出问题时先写清"做了什么 → 看到什么现象 → 预期是什么"，把这三行写下来往往就知道去哪查了。
