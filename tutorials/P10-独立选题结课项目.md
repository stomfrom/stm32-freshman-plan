## 0 · 开工前的准备

### 0.1 选题的尺度（最重要的一步）

**选对了题目，项目就成功了一半。**

| ❌ 太大 | ✅ 合适 | ✅ 也可以 |
|---|---|---|
| "智能家居系统" | "温湿度显示仪" | "倒计时器" |
| "四轴飞行器" | "按键密码锁" | "简易电子琴" |
| "机器人" | "超声波测距仪" | "智能小灯（光敏自动亮灭）" |

**判断标准**：能不能在 4 周内（每天约 2 小时）做出**能现场演示**的东西？

**推荐尺度**：**一个自己已经会做的功能 + 一两样新东西**。
- 纯用已学过的东西 → 学不到新东西，但**能保证做完**
- 全是新东西 → 大概率做不完
- **熟 + 新** 的组合最稳

### 0.2 本项目允许的选题池（供参考）

| 类型 | 题目 | 用到的外设 |
|---|---|---|
| 显示类 | 温湿度显示仪 | I2C + 传感器 + OLED |
| 显示类 | 数字时钟 | 定时器 + OLED + 按键 |
| 交互类 | 按键密码锁 | 按键 + OLED + Flash 存储 |
| 交互类 | 简易电子琴 | 按键 + 定时器 PWM + 蜂鸣器 |
| 控制类 | 智能小灯 | ADC(光敏) + PWM + 阈值控制 |
| 控制类 | 超声波测距仪 | 定时器输入捕获 + OLED |
| 数据类 | 电压记录仪 | ADC + Flash + 串口导出 |

### 0.3 时间安排建议（4 周）

| 周 | 做什么 | 交付节点 |
|---|---|---|
| 第 1 周 | 定题、写需求、列清单、**下单买器件**、搭最小系统 | 需求说明 + 器件清单（已下单） |
| 第 2 周 | 核心功能跑通（最难的那部分先做） | 能演示一个核心功能 |
| 第 3 周 | 补齐其余功能、模块化整理 | 全部功能能跑 |
| 第 4 周 | 异常测试、写文档、准备演示 | 四件套齐全 |

**⚠️ 器件第一天就下单**：物流要 3~7 天，等器件的时间要用来做软件。

## A1 · 自选题目写需求说明

**任务**：自选一个题目（如温湿度显示仪、倒计时器、简易电子琴、智能小灯、按键密码锁等），写一页需求说明：做什么、给谁用、至少要有什么功能。

### 知识点

**需求说明不是功能列表的堆砌**。它要回答三个问题：

| 问题 | 作用 |
|---|---|
| **做什么** | 一句话说清这个设备是干什么的 |
| **给谁用** | 用户是谁、什么场景（决定交互怎么设计） |
| **至少要有什么** | 最小可用功能集（划清底线，防止做不完） |

**"至少要有"是给自己划的安全线**：时间不够时，保住这些就算完成；有余力再加"最好有"。

### 操作步骤

照这个模板写**一页纸**：

```markdown
# 需求说明：<你的题目>

## 一句话说明
（例：一个能实时显示当前温度并刷新的小型显示仪）

## 给谁用、什么场景
（例：放在书桌上，用户随时看一眼当前温度；不需要联网，不需要历史记录）

## 至少要有（必须完成）
1. 能读取温度传感器数据
2. 能在 OLED 上显示温度（保留一位小数）
3. 每秒刷新一次，不闪屏
4. 上电即可工作，不需要连电脑

## 最好有（有余力再做）
1. 加一个按键，能在摄氏/华氏之间切换
2. 超过设定温度时 LED 报警

## 明确不做（划清边界，防止范围失控）
1. 不做联网上报
2. 不做历史数据存储
3. 不做手机 App
```

**"明确不做"这一节很关键**——它防止你中途不断加需求，最后什么都做不完。

### 验证方法

- 一页纸齐全（一句话说明 / 场景 / 至少要有 / 最好有 / 明确不做）
- "至少要有"不超过 5 条，且都**可验证**（不是"比较好用"这种模糊描述）
- 指导人确认过（任务要求"交给指导人确认后再动手"是从 A2 的清单开始，但需求建议先确认）

## A2 · 列出器件清单

**任务**：列出所需器件清单（元件名称 + 型号 + 数量 + 用途），交给指导人确认后再动手。

### 知识点

**为什么要写"用途"**：评审时会**随机抽查 3 个器件**，问"它在电路里起什么作用"。清单里写明用途，就是提前准备这个环节。

**型号要具体**：写"温度传感器"不够，要写清具体型号（如 `DS18B20` 或 `DHT11`），因为你得确认它**接口类型**（I2C/单总线/模拟）和**供电电压**（3.3V/5V）。

### 操作步骤

照这个模板列清单：

| # | 元件名称 | 型号 | 数量 | 用途 | 接口/电压 | 是否已有 |
|---|---|---|---|---|---|---|
| 1 | 温度传感器 | DS18B20 | 1 | 测温度 | 单总线 / 3.3V | 否 |
| 2 | OLED 显示屏 | 0.96" SSD1306 | 1 | 显示温度 | I2C / 3.3V | 是（P07 用过）|
| 3 | 上拉电阻 | 4.7kΩ | 1 | 单总线拉高 | — | 是（杂包）|
| 4 | 杜邦线 | 母对母 | 10 | 接线 | — | 是 |
| 5 | 5V 电源 | USB 供电 | 1 | 供电 | — | 是 |

**检查清单**（下单前逐项过）：

- [ ] 每个器件的**供电电压**与开发板匹配吗（3.3V / 5V）？
- [ ] **接口类型**与你的引脚规划一致吗（I2C / SPI / 单总线 / 模拟）？
- [ ] 有没有**需要独立供电**的（电机、大功率 LED、舵机）？
- [ ] 上拉/下拉电阻、去耦电容这些**小件**备齐了吗？
- [ ] 手头已有的不用重复买？

### 验证方法

- 清单有 5 列齐全（名称/型号/数量/用途/是否已有）
- **交给指导人确认过**（这是任务明确要求）
- 评审时被抽查 3 个器件，都能说清用途

## A3 · 画接线图或原理图

**任务**：画出接线图或原理图（手绘拍照、画图工具、嘉立创 EDA 均可），标出每个引脚接什么。

### 知识点

**接线图 vs 原理图**：

| | 接线图 | 原理图 |
|---|---|---|
| 关心什么 | **哪个引脚接到哪里** | 电气关系（含网络标号、元件符号）|
| 适合 | 面包板搭建、杜邦线连接 | 画 PCB、正式设计 |
| 本项目 | **接线图就够** | 想画也可以 |

**为什么必须画**：画的过程中你会**发现接口对不上的问题**（比如"这个传感器要 5V 但我只有 3.3V"、"这两个外设抢同一个引脚"）——在纸上发现比焊好之后发现便宜得多。

### 操作步骤

**手绘**（最快，拍照即可）：

```
        ┌──────────────────────────┐
        │  STM32F103C8T6 (蓝板)    │
        │                          │
   3.3V ●──────────────────────────● DHT11 VCC
        │                          │
        │  PB6 ●───────────────────● DHT11 DATA ──[4.7kΩ]── 3.3V
        │                          │
        │  PB7 ●───────────────────● DHT11 GND   ← 注意：别接错
        │                          │
        │  PB8 ●───────────────────● OLED SCL
        │  PB9 ●───────────────────● OLED SDA
        │                          │
   GND  ●──────────────────────────● OLED GND / DHT11 GND
        └──────────────────────────┘
```

**用工具画**（更清晰）：嘉立创 EDA、draw.io、甚至 PPT 都行。

**必须标出**：

- [ ] 每个外设接在**哪个引脚**（引脚号要具体）
- [ ] **供电**（3.3V / 5V / 独立电源）
- [ ] **共地**（所有器件 GND 必须连在一起）
- [ ] 上拉/下拉电阻的位置和阻值
- [ ] 引脚冲突检查（同一个引脚不能接两个功能）

### 验证方法

- 图上每个引脚标得清清楚楚
- 有供电与共地标注
- **无引脚冲突**
- 评审时能照着图接一遍线

### 常见问题

| 现象 | 原因 |
|---|---|
| 图上看着没问题，实际接不通 | 漏了共地 |
| 某个外设不工作 | 供电电压不匹配（5V 器件接 3.3V）|
| 两个功能互相干扰 | 引脚冲突（一个引脚配了两个功能）|

## A4 · 完成程序并做出演示成品

**任务**：完成程序编写与调试，做出一个能现场演示的成品（上电即可工作，不依赖电脑里的调试器）。

### 知识点

**"上电即可工作"是硬指标**：很多人的项目**接着调试器能跑，拔了就不行**。原因通常是：

| 原因 | 说明 |
|---|---|
| 程序没烧进 Flash | 只做了"在线调试"，没真正下载 |
| 依赖调试器的复位 | 没有正确的初始化顺序 |
| 依赖串口连接 | 某些外设初始化在等串口握手 |

**验收前必做**：拔掉烧录器、拔掉串口线，**只接电源**，上电看是否正常工作。

### 操作步骤

**1. 开发顺序：先做最难的核心功能**

不要从"点亮 LED"开始（那早就做过）。**先把最不确定的部分做通**：
- 不确定传感器能不能读通 → 先做传感器
- 不确定电机能不能转 → 先做电机

这样如果某个部分做不通，你有时间换方案。

**2. 每完成一个功能就 Git 提交**

```powershell
git add .
git commit -m "P10：温湿度读取功能完成并验证"
git push
```

保留可回退的版本——改坏了能立刻退回上一个好版本。

**3. 交付前必做"裸机测试"**

| 步骤 | 操作 |
|---|---|
| 1 | 拔掉 ST-Link 烧录器 |
| 2 | 拔掉串口线（如果有） |
| 3 | 只接电源（USB 或电池） |
| 4 | 上电，观察成品是否正常工作 |
| 5 | 连续运行 15 分钟，记录有无异常 |

### 验证方法

- **不接电脑、不依赖调试器，上电即可工作**
- 连续运行 **15 分钟**功能正常
- 板上有焊接/接线牢固（轻轻晃线不会断）
- 有演示视频（含完整操作流程）

### 常见问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 拔了调试器就不工作 | 没烧进 Flash | Keil 里正常 `Download`，不是 `Debug` |
| 上电后有时不启动 | 电源上电慢，初始化太早 | 初始化前加 `HAL_Delay(100)` 等待电源稳定 |
| 跑一会儿就不对了 | 栈溢出 / 内存泄漏（P09 学过） | 用栈水位与堆剩余检查 |
| 线一碰就断 | 杜邦线接触不良 | 换线，或焊上 |

## A5 · 至少实现 3 类外设功能

**任务**：至少实现 3 类来自前面项目的外设功能（如按键 + 显示 + 通信，或 ADC + PWM + 串口）。

### 知识点

**"3 类"是能力的证明**：它说明你不是只会点灯，而是能把多种外设**整合**在一个系统里协同工作。

**常见组合**：

| 组合 | 例子 |
|---|---|
| 按键 + 显示 + 采集 | 温湿度显示仪（按键切换单位）|
| 采集 + PWM + 显示 | 智能小灯（光敏采集 → PWM 调亮度 → 屏显亮度）|
| 按键 + 存储 + 显示 | 密码锁（按键输入 → Flash 存密码 → 屏显状态）|
| 通信 + 采集 + 定时 | 数据记录仪（ADC 采集 → 定时器采样率 → 串口导出）|

**每类功能要能"在演示中逐个指出并触发"**——所以要在演示脚本里安排好顺序。

### 操作步骤

列出你用到哪些外设，并准备演示触发方式：

| # | 外设类别 | 来自哪个项目 | 在成品中干什么 | 演示时怎么触发 |
|---|---|---|---|---|
| 1 | GPIO 按键输入 | P03/P04 | 切换显示单位 | 按一下按键 |
| 2 | I2C 显示 | P07 | 显示温度 | 上电即显示 |
| 3 | 定时器 | P05 | 每秒刷新 | 观察数字跳动 |
| 4 | （可选）串口 | P06 | 导出数据 | 打开串口助手 |

### 验证方法

- **至少 3 类**外设功能在成品中**真实工作**
- 演示时能**逐个指出并当场触发**
- 每类功能都能对应到前面学过的某个项目

## A6 · 提交四件套与 10 分钟讲解

**任务**：提交完整的四件套，并在评审时做 10 分钟讲解：需求 → 方案 → 遇到的最大难点 → 如果重做会改什么。

### 知识点

**四件套是什么**（贯穿整套方案）：

| # | 内容 | 要求 |
|---|---|---|
| 1 | **源码 / 设计文件** | 可编译、可打开、可复现 |
| 2 | **实测证据** | 截图/视频/波形/读数 |
| 3 | **README** | 原理 + 关键参数 + 踩坑 |
| 4 | **验收自测清单** | 勾选项，含"改一个需求还能跑"的验证 |

**10 分钟讲解的四段结构**（任务已给定）：

```
① 需求（1 分钟）   → 做什么、给谁用
② 方案（3 分钟）   → 系统框图、为什么这样选
③ 最大难点（3 分钟）→ 卡在哪、怎么解决的（这段最有价值）
④ 重做会改什么（2 分钟）→ 复盘
⑤ 留 1 分钟给追问
```

**"最大难点"这段是评审最看重的**——它证明你真的自己做过，而不是抄来的。

### 操作步骤

**1. 整理交付目录**

```
projects/P10-<你的题目>/
├── src/                  # 源码
├── hardware/             # 接线图/原理图
├── evidence/             # 截图、视频、日志
│   ├── demo.mp4
│   ├── serial_log.txt
│   └── abnormal_test.md
├── README.md
└── 验收自测清单.md
```

**2. 写 README**（必含）

```markdown
# P10 <题目>

## 一句话说明
## 系统框图（B1）
## 模块划分与接口（B2）
## 器件清单与用途
## 最大难点与解决过程
## 如果重做会改什么
```

**3. 准备讲解稿**

把 ②③ 两段的要点写成提纲（不用逐字稿），重点准备"最大难点"：

```markdown
## 最大难点
**现象**：温度读数偶尔跳变成 85.0℃（明显异常）
**排查过程**：
  1. 先怀疑传感器坏 → 换一个，问题依旧
  2. 用示波器看单总线波形 → 发现时序偶尔偏长
  3. 查手册 → 发现我的延时用 HAL_Delay（1ms 精度），
     而单总线要求微秒级时序
**解决**：改用 DWT 计数器做微秒延时
**结果**：连续测 100 次无跳变
```

**4. 准备"改需求"的答案**

评审会问："如果现在改一个需求，你要改哪几个文件？"
→ 提前想好一个例子（如"要加个按键切换单位，改 `app.c` 加事件处理 + `ui.c` 加显示分支，共 2 个文件"）

### 验证方法

- 四件套齐全
- 10 分钟讲解的四段都讲到了
- "最大难点"讲得具体（有现象、有排查过程、有解决）
- 能回答"改一个需求要动哪几个文件"

<a id="p10-b1"></a>
## B1 · 系统框图与数据流向

**任务**：写出系统框图，标出各模块之间的数据流向（谁产生数据、谁消费、通过什么方式传递）。

### 知识点

**框图的价值**：它是"代码结构"的图纸。画清楚了，写代码就是照着框图填实现。

**数据流向要标注传递方式**：

| 传递方式 | 什么时候用 |
|---|---|
| 全局变量 | 简单场景（但要小心竞争）|
| 队列 | 多任务之间（P09 学过）|
| 直接调用 | 同一任务内的函数调用 |
| 标志位 + 轮询 | 中断 → 主循环 |

### 操作步骤

画框图，**箭头标注数据流向**：

```
┌──────────────┐   raw value    ┌──────────────┐
│  传感器模块   │ ─────────────> │  数据处理模块 │
│ (dht11.c)    │                │ (process.c)  │
└──────────────┘                └──────┬───────┘
                                       │ 温度(float)
                                       v
┌──────────────┐  key event     ┌──────────────┐
│  按键模块     │ ─────────────> │  界面模块     │ ────> OLED
│ (key.c)      │                │ (ui.c)       │
└──────────────┘                └──────┬───────┘
                                       │ 状态变化
                                       v
                                ┌──────────────┐
                                │  上报模块     │ ────> 串口
                                │ (report.c)   │
                                └──────────────┘

数据流说明：
- 传感器 → 处理：直接调用（同一任务内），传原始值
- 按键 → 界面：事件方式（P04 的 key_get_event）
- 界面 → OLED：直接调用驱动接口
- 界面 → 上报：队列（若用 RTOS）
```

### 验证方法

- 框图里每个模块的**输入输出**都明确
- 标出了**数据流向与传递方式**
- 框图与实际代码结构一致（能指出每个框对应哪个文件）

## B2 · 模块化封装

**任务**：做到模块化：至少把 2 个功能封装成独立的 `.c` / `.h` 模块，模块对外接口清晰、应用层不碰底层寄存器。

### 知识点

**判断模块化是否到位**——问自己三个问题：

1. 这个模块能不能**不改代码就换引脚**？（能 = 封装到位）
2. `main.c` 里有没有直接操作寄存器的代码？（有 = 没封装好）
3. 想换一个传感器，要改几个文件？（只想改 1 个 = 好）

**标准模块结构**：

```
<模块名>.h   ← 对外接口（别人只 include 这个）
<模块名>.c   ← 实现细节（外面看不到）
```

### 操作步骤

**示例：把传感器封装成模块**

`dht11.h`：

```c
#ifndef __DHT11_H
#define __DHT11_H

#include <stdint.h>

/* 返回 0 成功，-1 失败（校验错/超时） */
int  dht11_init(void);
int  dht11_read(float *temp_c, float *humi_pct);

#endif
```

`dht11.c`：

```c
#include "dht11.h"
#include "main.h"      /* 引脚宏定义 */

/* 所有底层细节关在这里：GPIO 操作、微秒延时、时序 */
static void dht11_set_output(void) { /* ... */ }
static void dht11_set_input(void)  { /* ... */ }
static int  dht11_wait_level(GPIO_PinState lv, uint32_t timeout_us) { /* ... */ }

int dht11_init(void) { /* ... */ }

int dht11_read(float *temp_c, float *humi_pct)
{
    /* 完整时序实现，外部完全不用管 */
}
```

**应用层（main.c）变得干净**：

```c
#include "dht11.h"

float t, h;
if (dht11_read(&t, &h) == 0)
{
    printf("T=%.1f C  H=%.1f %%\r\n", t, h);
}
else
{
    printf("sensor read failed\r\n");
}
```

### 验证方法

- 至少 2 个模块独立成 `.c` / `.h`
- **应用层里搜不到寄存器操作**（如 `GPIOA->`）和底层 HAL 调用
- 每个模块的 `.h` 接口简洁（5~8 个函数以内）
- 能回答："要换一个传感器，改哪几个文件？"（答：只改那个模块的 `.c`，应用层不动）

## B3 · 写使用说明

**任务**：为成品写一份使用说明（怎么接电、怎么操作、每个按键或每步操作的效果），让别人不看代码也能用起来。

### 知识点

**合格标准**：**另一个人不看代码也能把成品用起来**。

**评审时会现场验证**：请一位没参与的同学照着你的说明书操作一遍。他卡住的地方，就是你说明书写漏的地方。

照这个模板写 `使用说明.md`：

```markdown
# <成品名> 使用说明

## 一、需要什么
- 成品本体
- 供电：USB 线一根（或 5V 电源）
- 不需要电脑

## 二、怎么启动
1. 用 USB 线接上电源（插到充电器或电脑 USB 口都行）

## 三、怎么操作
| 操作 | 效果 |
|---|---|
| 按一下 K1 | 摄氏 / 华氏 切换 |
| 长按 K1（>1秒）| 进入/退出报警设置 |
```

## B4 · 异常场景测试

**任务**：做一次异常场景测试：断电重上电、按键连按、输入超范围等至少 3 种情况，记录现象并说明处理方式。

### 知识点

**为什么要测异常**：正常流程谁都能跑通。**异常场景才暴露真实问题**——而这些正是演示时最容易翻车的地方。

**必须测的三类**：

| 场景 | 测什么 | 期望 |
|---|---|---|
| **断电重上电** | 反复上下电 5~10 次 | 每次都能正常启动（关键是电源稳定后的初始化）|
| **按键连按** | 快速狂按 | 不死机、不错乱、不丢事件或少丢 |
| **输入超范围** | 给超出量程的输入 | 不崩溃，显示合理（如"超量程"提示）|

### 操作步骤

逐项测试并填表：

| # | 异常场景 | 操作方式 | 观察到的现象 | 是否正常 | 处理方式 |
|---|---|---|---|---|---|
| 1 | 断电重上电 | 连续上下电 10 次 | | ✅/❌ | |
| 2 | 按键连按 | 1 秒内按 10 次 | | ✅/❌ | |
| 3 | 输入超范围 | 把传感器拔掉 / 给超量程输入 | | ✅/❌ | |
| 4 | 快速拔插电源 | 上电中途断电再上电 | | ✅/❌ | |
| 5 | （自选）传感器断开 | 运行中拔掉传感器 | | ✅/❌ | |

**每项都要写"处理方式"**——即使结果是"没出问题"也要写，说明你**为什么**觉得没问题。

### 验证方法

- 至少 3 种异常场景都有记录（现象 + 是否正常 + 处理方式）
- 没有"测了但没记录"的情况
- 对不正常的项，说明你做了什么处理（或为什么决定不处理）

```markdown
## <你的名字/学号> · P10 结课项目

- **现象**：DHT11 偶尔读出 85.0℃ 这种明显异常值
```

## B6 · 接受随机追问

**任务**：在评审中回答随机追问：随便挑一段代码讲清它的作用、随机改一个小需求说明你要改哪几个文件。

### 知识点

**追问的目的不是难为你，而是确认"这是你自己做的"**。抄来的代码，一问就露馅。

**两类追问及准备方法**：

| 追问类型 | 怎么准备 |
|---|---|
| "这段代码干什么？" | 评审前**自己逐段过一遍代码**，特别是从例程拷来的部分 |
| "改个需求要动哪几个文件？" | 提前想好 1~2 个例子，理清模块边界 |

### 操作步骤

**1. 自查代码**（评审前必做）

对着自己的代码问：

- [ ] 每个函数我都能说清作用吗？
- [ ] 有没有从例程拷来但我不理解的代码？（**有就现在搞懂**）
- [ ] 我用的每个外设，初始化参数为什么这么设？
- [ ] 那个"魔数"（如 `0x1FC00`）代表什么？

**2. 准备"改需求"的答案**

提前想好例子：

```markdown
## 改需求示例
**问**：如果要把刷新频率从 1 秒改成 500ms，要改哪几个文件？
**答**：只改 1 处 —— `app.c` 里的刷新周期常量（`REFRESH_MS`）。
     因为我把周期抽成了宏，显示逻辑是参数化的，不用动。

**问**：如果要加一个"温度超过 30℃ 时 LED 报警"的功能呢？
**答**：改 2 个文件 —— `app.c` 加阈值判断与调用，`led.c` 加报警闪烁接口。
     不需要动传感器模块和显示模块。
```

**3. 诚实原则**

遇到不懂的：**直接说不懂，然后说你会怎么去搞懂**。

```c
"这段是例程里带的，我目前还不能完全解释清楚。
 我的理解是……如果需要我可以现在查手册确认。"
```

> 这比硬编一个错误答案好得多。**评审看的是态度与潜力，不是全知全能。**

### 验证方法

- 能讲清自己的代码（评审随机挑段都能说）
- 能回答"改需求动哪几个文件"
- 不懂时能诚实承认并说清补救路径
